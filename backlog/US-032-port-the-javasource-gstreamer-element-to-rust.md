# US-032 — Port the javasource GStreamer element to Rust inside fxplugins

**Status:** 📋 Ready (drafted 2026-09-30 from a read-only survey; read: `javasource.c` excerpts (pads, signals,
properties, locking, both buffer paths), `fxplugins.c`, the `fxplugins` CMake targets, `gstreamer-lite.def`, the
jfxmedia signal wiring; lines counted with `git ls-files | xargs wc -l`; not checked: how gstreamer-rs's `-sys`
link names are overridden, gstreamer-rs's panic trampolines and signal marshalling, which gstreamer-lite symbols
gstreamer-rs pulls in; nothing built; 2026-10-01: the file deletion moved behind US-028 after a re-read of the
macOS `fxplugins` target, `native/mac.cmake:603-625`) · **Epic:** Rust port of the remaining native code (goal 3) ·
**Blocked by:** US-027, US-041 (fxplugins map-misuse fix); the file deletion (slice 4) also by US-028

## Story
As a platform maintainer,
I want the `javasource` element, which feeds GStreamer pipelines from the Java stream callbacks, implemented in
Rust inside the existing `fxplugins` library,
so that its cross-thread state and the Java-sized buffer copies are checked by the compiler, and the fork has a
proven way to build Rust GStreamer elements against gstreamer-lite.

## Why Rust fits here
Paths relative to `modules/javafx.media/src/main/native/` unless they start with `native/` or `FFM-STATUS.md`
(those are under `modules/javafx.media/`).
- **Must stay native (R1):** `javasource` is a `GstElement` subclass
  (`gstreamer/plugins/javasource/javasource.c:87`, `:120`). GStreamer calls its pad functions on its own threads:
  a pad task in push mode (`:391`, `:505`) and `getrange` in pull mode (`:296`). Java reaches it only at stream
  level, through the six signals jfxmedia connects to the Java stream callbacks
  (`jfxmedia/platform/gstreamer/GstPipelineFactory.cpp:236-260`). It is neither a WRAPPER nor a PURE function.
- **Owned code (R2):** OpenJFX code; the FFM migration edited it (`FFM-STATUS.md:118-122`).
- **Buildable and testable here (R3):**
  - It is compiled into `fxplugins` on Windows and Linux (`native/win.cmake:753-754`, `native/linux.cmake:369-370`).
    macOS compiles it too (`native/mac.cmake:610-611`) and keeps the C until US-028 (P2).
  - It is the pipeline's source element (`GstPipelineFactory.cpp:230`), so `MediaPlaybackTest` runs through it:
    executed on Windows x64, and run by CI Linux against a null ALSA device (`FFM-STATUS.md:252-268`).
- **Benefit (R4):**
  - **Cross-thread state.** `position` and `pending_event` are shared by the pad task and the application thread
    under one `GMutex` (`javasource.c:89`, `:386-397`, `:452-454`, `:540-542`, `:580-582`). In Rust the lock owns
    the state, so an unlocked access does not compile.
  - **Sizes from Java.** Java returns the size the element allocates (`:639-642`), and the copy counts are checked
    by hand (`:662`, `:880`). In Rust they become slice bounds.
  - **Read maps.** The pull path wrote through a read map (`:862`, `:883`); that is fixed in C first by the
    blocking story. With gstreamer-rs, a readable map is `&[u8]`, so the same mistake would need `unsafe`.
  - **Groundwork.** This is the smallest owned element (1,078 hand-written lines). It proves the link,
    registration and panic setup that the progressbuffer and mfwrapper ports reuse.
- **Binding (R5):** `gstreamer`, `glib` and their `-sys` crates (GStreamer project, gtk-rs-core;
  `MIT OR Apache-2.0`, MIT taken, from knowledge; the toolchain story's licence audit confirms), over
  gstreamer-lite 1.28.3 (`gstreamer/gstreamer-lite/gstreamer/gst/gstversion.h:51-63`). Only `ElementImpl` is
  needed: the C derives from `GstElement`, and Windows gstreamer-lite exports no `gst_base_src_*`.
- **Why not Java:** GStreamer calls pad functions at buffer rate on its own threads. A Java element would need an
  upcall per pad callback plus GObject type registration from Java. The Java side of this path already exists:
  the stream callbacks behind the signals.

## Current state
- **Files.** `gstreamer/plugins/javasource/`: `javasource.c` 1,024 and `javasource.h` 54 lines, hand-written.
  `marshal.c` 250 and `marshal.h` 52 lines are generated by `genmarshal.sh` (4) from `marshal.in` (14), for the
  five non-stock signal signatures. Total 1,398.
- **Element contract.** It is the ABI here: there is no `*_api.h`, and jfxmedia binds by factory and signal
  name.
  - **Factory.** `javasource` (`javasource.h:33`), registered by `java_source_plugin_init` (`javasource.c:1021`),
    which `fxplugins_init` calls (`gstreamer/plugins/fxplugins.c:43`).
  - **Pad.** One always `src` pad (`javasource.c:154`) with activatemode, event, getrange and query functions
    (`:292-298`).
  - **Properties.** `size`, `is-seekable`, `is-random-access`, `stop-on-pause`, `hls-mode`, `location`,
    `mimetype` (`:197-221`).
  - **Signals.** `seek-data`, `read-next-block`, `read-block`, `copy-block`, `close-connection`, `property`
    (`:224-277`), with the signatures in `marshal.in`. `read-block` is connected only for random-access sources
    (`GstPipelineFactory.cpp:259-260`).
  - **Return codes.** EOS, HLS "more data" and error codes from `read-next-block` (`javasource.c:723-735`); a
    zero size is deliberately unhandled (`:735`). HLS property requests at `:786`.
- **Threads.** The pad task (`java_source_loop`), GStreamer's pull thread (`getrange`), and the application
  thread (seek `:519`, state changes).
- **Exports.** `gst_plugin_desc` (`fxplugins.c:55`, `dllexport` on Windows), which gstreamer-lite resolves after
  loading the names in `gstlite_plugins_list` (`gstreamer/gstreamer-lite/gstreamer/gst/gstregistry.c:271-283`).
  On Linux, default visibility also exports every non-static C function of the library.
- **Tests.** `MediaPlaybackTest` (2), `JfxMediaNativeTest` (23); the module suite is 33 (`FFM-STATUS.md:256-261`).
  Nothing observes the element's caps, buffers or events directly.

## Approach
- **Contract unchanged.** Same factory name, rank, GType name and pad template; same properties (names, types,
  ranges, defaults, flags); same signal names, signatures and return-code meanings; same event and query answers,
  and the same thread for every callback. `fxplugins.c` stays C and keeps `gst_plugin_desc`. The crate exports
  `java_source_plugin_init` with the C prototype, so the C caller pulls the member in, and `java_source_get_type`
  if the pre-port export list has it.
- **Crate.** `fxplugins-rs` (staticlib) in the US-027 layout
  (`modules/javafx.media/src/main/native-rust/fxplugins/`), one module per element. The progressbuffer
  and mfwrapper ports add modules to it. It uses the `gstreamer` and `glib` crates with no `v1_xx` feature beyond
  what the code needs, and no `gstreamer-base`.
- **Link recipe.** Settled in slice 2 and recorded with the toolchain story.
  - The `-sys` link names resolve to `gstreamer-lite` on both OSes and to `glib-lite` on Windows. Linux keeps the
    system GLib (`native/linux.cmake:66-67`).
  - Every symbol the Rust side needs that `gstreamer/projects/win/gstreamer-lite.def` (155 `NONAME` ordinals)
    lacks is appended with a new ordinal. Known so far: `gst_pad_template_new`, `gst_pad_template_new_with_gtype`,
    `gst_plugin_get_type`.
  - There are no debug categories, because everything builds with `GST_DISABLE_GST_DEBUG`
    (`native/win.cmake:778`, `native/linux.cmake:380`).
- **Panics.** Every pad function, property and signal path returns the C's failure value (`GST_FLOW_ERROR`,
  `FALSE`, the C's error code) under gstreamer-rs's per-callback panic guard. A caught panic is a bug.
- **Mixed transition.** A CMake option (named by the toolchain story's convention) drops `javasource.c` and
  `marshal.c` from the `fxplugins` sources and links the crate instead. macOS keeps the option off until US-028
  (P2).
- **Parity harness.** A test-only native trace driver, not shipped, reused by the later ports.
  - It cannot be a Java FFM test: Windows gstreamer-lite exports by ordinal, and `SymbolLookup` resolves names
    only.
  - It links gstreamer-lite's import library, loads `fxplugins` as the registry does, and builds `javasource`
    with a recording sink. A scripted fake stream answers the six signals.
  - It prints a canonical text trace: caps; segment and custom events with every field; each buffer's offset,
    size, flags and content hash; EOS; error messages with domain and code; each signal emission with arguments
    and return; and the thread role of each line.

### Slices
1. **Goldens from C.**
   - Add the trace driver.
   - Record `fxplugins`' export lists (`dumpbin /exports`, `nm -D --defined-only`).
   - Capture an introspection golden: factory, rank, GType name, pad template, and every property and signal with
     its full spec.
   - Capture trace goldens at a recorded commit on Windows and WSL, over this corpus: push mode to EOS; pull mode
     with random reads, including the last partial block; seek in both modes, including `seek-data` failing;
     `read-next-block` returning the EOS, error and HLS "more data" codes, and zero; a short `copy-block`;
     `stop-on-pause` true and false across PAUSED/PLAYING; HLS duration and property requests;
     `close-connection` on dispose; no `read-block` handler.
2. **Rust javasource behind the option.**
   - Crate, link recipe and `.def` additions (listed in the PR, each with the call that needs it).
   - The whole element as one translation unit.
   - Gate: introspection and trace goldens exact on Windows and WSL. The module's Java suite passes with the
     option on. With the option off, the build is identical to today.
3. **Remove the C from the Windows and Linux builds.** In its own commit, once slice 2 is accepted on both, drop
   `javasource.c` and `marshal.c` from the `fxplugins` sources in `native/win.cmake` and `native/linux.cmake`. On
   those two OSes the option goes too. The files and the full `javasource.h` stay, because macOS still compiles
   them (`native/mac.cmake:610-611`, include directory `:615`).
4. **Delete the C, after US-028.** Remove `javasource.c`, `marshal.c`, `marshal.h`, `marshal.in` and
   `genmarshal.sh`, and their `native/mac.cmake` lines. `javasource.h` shrinks to the init prototype
   `fxplugins.c:28` includes. Remove the option.

## Acceptance criteria
- Windows `dumpbin /exports fxplugins.dll` is identical to the slice-1 list.
- Linux `nm -D --defined-only libfxplugins.so` is identical except for symbols internal to the C files the Linux
  build no longer compiles, each listed in the PR. No Rust std symbol is exported.
- Introspection and trace goldens exact on Windows and WSL. The goldens are never edited to pass.
- The 33-test module suite unchanged and passing.
- `gstreamer-lite.def` changes only by appended entries.
- After slice 3, `javasource.c` and `marshal.c` are absent from `native/win.cmake` and `native/linux.cmake`, and
  `native/mac.cmake` is unchanged. After slice 4, the slice-4 files are deleted and nothing references them
  (`git grep`).
- `unsafe` only in the crate's `ffi` module: the init export and the `copy-block` pointer hand-off. Each block
  has a `// SAFETY:` comment.
- clippy and rustfmt clean.

## Definition of Done
PR merged after review by the maintainer; verified on Windows and on WSL Linux; the C removed from the Windows and
Linux builds, and deleted from the tree by slice 4 once US-028 has landed; the link recipe recorded where the
toolchain story keeps build notes; the Rust table in `backlog/README.md` updated.

## Risks
| # | Risk | Mitigation |
| --- | --- | --- |
| 1 | The `-sys` crates cannot be pointed at `gstreamer-lite`/`glib-lite` without patching | Slice 2 settles it before logic is reviewed; a vendored patch of their build scripts is acceptable and recorded |
| 2 | gstreamer-rs pulls in many symbols missing from the ordinal-only `.def` (MSVC reports unresolved externals even for unused crate functions) | Append what the linker names; if the list is unreasonable, fall back to the `-sys` crates with local safe wrappers and say so in the PR |
| 3 | Rust-defined signals run jfxmedia's C handlers through GLib's generic marshaller instead of the generated `marshal.c` | The trace records every argument and return; "no handler connected" (`read-block`) is in the corpus |
| 4 | gstreamer-rs's initialisation checks or type registration behave differently inside a plugin loaded by gstreamer-lite | Introspection golden on both OSes in slice 2 |
| 5 | Event order or EOS timing changes | Traces exact; no new threads or locks (port rule P6) |
